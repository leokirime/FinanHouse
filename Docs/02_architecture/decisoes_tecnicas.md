### DT-19 — Persistência atômica de compra parcelada via `db.transaction()` nativo (RS-01, Sessão 12, Bloco 04)

- **Data:** 2026-08-25
- **Contexto:** RS-01 (`Docs/05_sessions/session_12_parcelamentos_e_compromissos_futuros/02_analysis/analise_riscos.md`) exigia uma decisão formal obrigatória neste bloco: uma compra parcelada (`InstallmentPlan` + N `FinancialEntry` + eventuais `MonthlyPeriod` novas) precisa nascer como uma única operação atômica — nenhum estado parcial é aceitável em caso de falha no meio da criação das N parcelas. A análise de risco já registrava preferência explícita por uma solução atômica real (`db.transaction()`) sobre compensação em código de aplicação, condicionada à viabilidade da arquitetura de persistência existente.
- **Decisão:** a arquitetura já suportava transação nativa sem nenhuma mudança estrutural — confirmado por inspeção antes de implementar (`create-drizzle-repositories.ts`/`types.ts`, escritos no Bloco 14, já documentavam explicitamente que tanto a instância `MySql2Database` quanto o `tx` de `db.transaction()` satisfazem `DrizzleDb`, o tipo aceito por todo repositório) e por precedente já em produção (`db-bootstrap-household.ts`, `db-configure-initial-passwords.ts`, os quatro scripts `db-smoke-*.ts`).
  - **`InstallmentTransactionRunner`/`InstallmentTransactionContext`** (porta nova, `application/ports/`): abstração de unidade de trabalho — a camada de aplicação (`CreateInstallmentPurchaseService`) nunca importa `mysql2`/`drizzle-orm` diretamente, só enxerga `run(work: (context) => Promise<T>): Promise<T>`, onde `context` expõe `installmentPlans`/`entries`/`periods`/`categories` — os únicos repositórios necessários para a operação.
  - **`DrizzleInstallmentTransactionRunner`**: implementação real — `this.db.transaction(async (tx) => { ... construir os 4 repositórios com tx ... })`. Nenhuma lógica de rollback própria: é inteiramente responsabilidade do MySQL/Drizzle — qualquer exceção lançada dentro do callback aborta a transação e desfaz todas as escritas feitas através de `tx`. Nenhum erro é reembrulhado no nível do runner (erros de domínio lançados dentro de `work` — ex.: `CategoryNotFoundError` — chegam ao chamador sem serem mascarados como erro de persistência; cada repositório já sanitiza seus próprios erros de driver internamente, como desde DT-10).
  - **`InMemoryInstallmentTransactionRunner`**: reproduz atomicidade real (não apenas nominal) para testes sem banco — tira snapshot de `installmentPlans`/`entries`/`periods` antes de `work`, restaura o snapshot se `work` lançar. Deliberadamente **não inclui o contador de id no snapshot/restore**: um `AUTO_INCREMENT` real do MySQL nunca é "devolvido" por um `ROLLBACK` (o contador avança de forma monotônica e definitiva mesmo quando o `INSERT` correspondente é desfeito — por isso lacunas de id são normais e nunca um bug). Reverter o contador junto com os dados criaria um comportamento mais permissivo que o banco real, mascarando um possível reaproveitamento de id que nunca aconteceria em produção — testado explicitamente.
  - **`CreateInstallmentPurchaseService`** roda inteiramente dentro de `transactionRunner.run(...)`: valida categoria (existe + pertence ao household, antes de qualquer escrita, não confia só na FK composta), cria o plano (`createInstallmentPlan` + `installmentPlans.create()`, `id` real via `insertId`), gera as parcelas (`generateInstallments`, puro), resolve cada competência (reaproveita ou cria via `openMonthlyPeriod` + `periods.create()`, mesma função de domínio do fluxo manual de abertura de competência) e cria cada `FinancialEntry` reaproveitando `createFinancialEntry` (a mesma função usada pelo lançamento avulso) — nenhuma regra de domínio duplicada, incluindo a rejeição automática se uma competência pré-existente já estiver fechada/em revisão.
  - **`FinancialEntry` (domínio) estendida** com `installmentPlanId: number | null`/`installmentNumber: number | null` — campos obrigatórios (nunca `?:`) para que toda construção declare explicitamente se é lançamento avulso (ambos `null`) ou parcela (ambos preenchidos), nunca deixando a relação ambígua por omissão. `createFinancialEntry` aceita os dois campos como entrada opcional (default `null`), preservando 100% de compatibilidade com o fluxo de criação avulsa existente sem exigir nenhuma mudança nos chamadores atuais.
- **Por que não uma solução de compensação:** a alternativa cogitada pela análise de risco (reverter em código de aplicação as parcelas já criadas antes de propagar o erro) foi descartada porque a solução atômica se mostrou viável sem nenhuma mudança estrutural — compensação manual sempre deixa uma janela onde o processo pode morrer entre a falha original e a reversão, recriando exatamente o problema que RS-01 queria eliminar.
- **Testado:** `DrizzleInstallmentTransactionRunner` — wiring (uma transação por chamada, contexto com instâncias reais dos 4 repositórios, erro de domínio propagado sem reembrulho). `InMemoryInstallmentTransactionRunner` — sucesso persiste tudo; rollback total nos 6 pontos de falha exigidos (plano, parcela 1, parcela intermediária 6/10, última parcela 10/10, competência nova, categoria de outro household antes de qualquer escrita); dados pré-existentes à transação nunca são afetados por um rollback; ids nunca reaproveitados após rollback. `CreateInstallmentPurchaseService` — os mesmos 6 cenários de falha end-to-end, divisão exata de valores (`splitMoney`, incluindo R$ 1000,00/3 = 333.33+333.33+333.34), datas (virada dezembro→janeiro, `dueDay` 31 em janeiro/fevereiro/fevereiro bissexto/abril), isolamento e visibilidade compartilhada por household, compatibilidade com lançamento avulso. HTTP: `POST`/`GET` lista/`GET` detalhe, validação de corpo, autenticação, escopo de household/categoria, formato monetário, `installmentCount` sem máximo arbitrário (61 aceito). Suíte completa: API 667 (+43), Web 366 (inalterado, só ajuste estrutural de fixture), Domain 214 (+2).
- **Consequências:** RS-01 passa a **RESOLVIDA**. Nenhuma migration nova foi necessária — a transação opera sobre o schema já aplicado no Bloco 03. Nenhum wiring de DI pré-existente precisou de reestruturação além de acrescentar o novo runner como uma dependência própria de `createHttpApp` (`installmentTransactionRunner`, deliberadamente fora de `HttpAppRepositories`, que representa repositórios não-transacionais). Frontend recebeu apenas o ajuste estrutural mínimo (`FinancialEntryDto`/`financialEntryFromDto` do lado do cliente, para acompanhar a extensão do tipo de domínio compartilhado) — nenhuma tela nova, reservada ao Bloco 05.

### DT-18 — DT-15 corrigida por completo: `financial_entries`, `monthly_periods` e `category_budgets` também usam `AUTO_INCREMENT` nativo (rodada de correção/hardening pré-Bloco 04)

- **Data:** 2026-08-20
- **Contexto:** DT-17 (mesmo dia) reavaliou formalmente o risco documentado como dívida técnica P2 em DT-15 e concluiu que ele era real — não apenas teórico — especificamente para o padrão de uso que o Bloco 04 pretende introduzir (criação sequencial de N `FinancialEntry` a partir de um único `InstallmentPlan`). Em vez de corrigir isoladamente apenas `FinancialEntryRepository`, o proprietário autorizou fechar a dívida técnica **por completo** nos três repositórios ainda pendentes desde DT-15 (`DrizzleFinancialEntryRepository`, `DrizzleMonthlyPeriodRepository`, `DrizzleCategoryBudgetRepository`) antes de iniciar o Bloco 04 — para não carregar nenhuma implementação baseada em `information_schema.TABLES.AUTO_INCREMENT`/`nextId()`/cálculo manual de chave primária para a próxima fase do projeto.
- **Decisão:** os três repositórios seguem agora exatamente o mesmo padrão já usado por `AuthSessionRepository` (DT-15) e `InstallmentPlanRepository` (DT-17): `create()`/`update()` como métodos separados, nunca um `save()` ambíguo que decide entre INSERT/UPDATE a partir de um `id` pré-calculado.
  - **`create(entity: Omit<Entity, 'id'>): Promise<Entity>`** — sempre um `INSERT` novo, nunca fornece `id`; o valor real vem de `ResultSetHeader.insertId`, lido de volta pelo próprio banco de forma atômica.
  - **`update(entity: Entity): Promise<Entity>`** — só toca uma linha já existente do mesmo household; verifica existência e household antes do `UPDATE` (mesma checagem combinada num único `if`, mesmo padrão de `DrizzleAuthSessionRepository.update()`) e lança `HouseholdScopeViolationError` tanto para id inexistente quanto para household divergente — nunca cria implicitamente.
  - **`nextId()` removido inteiramente** das três portas (`FinancialEntryRepository`, `MonthlyPeriodRepository`, `CategoryBudgetRepository`) e das três implementações Drizzle — nenhuma leitura de `information_schema` remanescente, nenhum cálculo de `MAX(id)`.
  - **Serviços de aplicação adaptados sem alterar nenhuma regra de negócio:** cada uso de `nextId()` + função de domínio + `save()` virou `create()` direto a partir do resultado da função de domínio (com um `id: 0` descartado no input da função de domínio — nunca usado por ela em validação, só copiado para a entidade retornada — e removido antes de chamar `create()`); cada uso de `save()` para transição de estado (marcar pendente, realizar, cancelar, fechar competência, etc.) virou `update()`. Nenhum comportamento observável mudou: `CreateFinancialEntryService`, `OpenMonthlyPeriodService`, `PutCategoryBudgetService` e todos os demais continuam com a mesma assinatura pública e as mesmas regras de domínio.
  - **Repositórios em memória** (`InMemoryFinancialEntryRepository`, `InMemoryMonthlyPeriodRepository`, `InMemoryCategoryBudgetRepository`) passaram para o mesmo contrato `create()`/`update()`, com `id` sempre gerado internamente (contador simples, nunca equivalente ao bug de `information_schema` — nunca tiveram esse problema, mas a interface precisava ficar consistente com a porta). Ganharam também `seed(entities: T[]): void` — mesmo padrão já usado por `InMemoryUserRepository`/`InMemoryCategoryRepository`/etc. — para que os ~70 testes de HTTP/serviço pré-existentes continuem populando estado inicial conhecido (com `id` explícito) sem depender de `create()`/`update()`, que agora aplicam regras de negócio (nunca cria implicitamente, nunca aceita `id` do chamador).
  - **Proteção de concorrência preservada sem lógica nova:** `monthly_periods_household_reference_month_unique` e `category_budgets_household_period_category_unique` continuam sendo a barreira real contra duplicidade. Uma colisão em `create()` (ex.: duas requisições `PUT .../periods/:referenceMonth` quase simultâneas para a mesma competência) agora falha como `DuplicateRecordError` (409, sanitizado) — nunca mais como sobrescrita silenciosa de `id`, que era o modo de falha do padrão antigo. Avaliado explicitamente e decidido **não** adicionar nenhuma lógica de nova leitura/retry: a rota já é idempotente na leitura (`GET` antes do `PUT`), o erro sanitizado já é uma resposta segura e visível, e nenhum outro fluxo do projeto implementa retry otimista — adicionar um aqui introduziria um padrão novo sem necessidade comprovada (aplicação de household único, sem escritores concorrentes reais até hoje).
  - **`FinancialEntry` parcelada (Sessão 12) permanece compatível:** `installmentPlanId`/`installmentNumber` (colunas nullable do Bloco 03) não fazem parte do tipo de domínio `FinancialEntry` — `create()`/`update()` continuam usando exclusivamente esse tipo; a leitura de uma linha com essas colunas preenchidas nunca quebra o mapeamento (testado explicitamente). A criação atômica de plano + N parcelas (RS-01) continua fora de escopo — reservada ao Bloco 04, que agora pode implementá-la sobre um `create()` seguro, sem a dívida técnica que motivou esta correção.
- **Testado:** os três testes de repositório Drizzle foram reescritos (`FakeDrizzleDb`) cobrindo: `create()` sem `id` fornecido, `insertId` como origem do `id` real, duas chamadas sequenciais com `id`s distintos, `create()` nunca virando `UPDATE` disfarçado, `update()` nunca criando implicitamente (id inexistente rejeitado), `update()` nunca alterando o household de um registro existente, falhas de driver sempre sanitizadas (`PersistenceError`), o comportamento de negócio pré-existente preservado (coluna auxiliar do membro responsável, conflito de unicidade de competência/limite como `DuplicateRecordError`), e um teste estático por arquivo garantindo que o código-fonte real (fora de comentários) nunca menciona `information_schema`/`nextId`/`MAX(id)` e sempre usa `insertId` — mesmo padrão já usado pelos guards de `DrizzleAuthSessionRepository`/`DrizzleInstallmentPlanRepository`. Suíte completa sem regressão: API 624 (+15 sobre o baseline do Bloco 03, todos nos três arquivos de teste reescritos), Web 366 (inalterado), Domain 212 (inalterado).
- **Consequências:** `git grep -n "\.nextId("` em `apps/**` não retorna nenhuma ocorrência executável — a dívida técnica P2 registrada em DT-15 para estes três repositórios está **resolvida**, não apenas mitigada. Dois scripts de smoke-test manuais (`db-smoke-repositories.ts`, `db-smoke-category-budgets.ts`, nenhum executado nesta rodada) foram atualizados para o novo contrato, mantendo a mesma cobertura de cenário (criação, leitura após escrita, atualização, rejeição de household divergente, isolamento). Nenhuma migration nova foi necessária — a correção é inteiramente de código de aplicação sobre colunas `AUTO_INCREMENT` que já existiam desde a migration inicial.

### DT-17 — Persistência de `InstallmentPlan` (schema/migration) e reavaliação formal do risco de DT-15 para `financial_entries` no contexto do Bloco 04

- **Status (risco):** o achado de risco (seção "Reavaliação formal do risco de DT-15...") foi tratado pela DT-18, na mesma data — os três repositórios afetados (`FinancialEntryRepository` incluído) não usam mais `nextId()`/`save()`.
- **Status (migration):** a migration `0004_deep_machine_man.sql`, gerada e revisada nesta decisão, foi **aplicada em 2026-08-20 ao banco real de desenvolvimento `finanhouse_dev` (Aiven)**, com autorização explícita do proprietário — auditoria somente leitura antes/depois (fora do conjunto oficial de scripts, script temporário removido após uso) confirmou: journal do Drizzle com cinco migrations registradas (antes: quatro); tabela `installment_plans` criada com zero registros; colunas `financial_entries.installment_plan_id`/`installment_number` presentes e nullable; as quatro foreign keys (`installment_plans_household_id_households_id_fk`, `installment_plans_created_by_user_id_users_id_fk`, `installment_plans_category_household_fk`, `financial_entries_installment_plan_household_fk`) todas `ON DELETE RESTRICT`, nenhuma `CASCADE`; os dois índices `UNIQUE` (`installment_plans_id_household_id_unique`, `financial_entries_installment_plan_number_unique`) presentes; as quatro `CHECK` constraints presentes; `installment_plans.id` com `auto_increment`; `first_reference_month` como `date`; `total_amount` como `decimal(13,2)`; e as contagens das oito tabelas estruturais anteriores (`users`, `households`, `household_members`, `categories`, `monthly_periods`, `financial_entries`, `category_budgets`, `auth_sessions`) idênticas antes e depois — nenhum dado real foi inserido, alterado ou removido; nenhum seed/bootstrap executado; produção (`finanhouse_prod`) não foi acessada. Ver `database/migrations/README.md` e `Docs/03_contracts/contrato_banco_dados.md` para o registro correspondente.

- **Data:** 2026-08-20
- **Contexto:** Sessão 12, Bloco 03. O domínio puro de parcelamentos (Bloco 02: `InstallmentPlan`, `GeneratedInstallment`, `createInstallmentPlan`, `generateInstallments`) precisava de uma camada de persistência real antes que o Bloco 04 possa orquestrar a criação atômica de um plano + N parcelas (RS-01, ainda fora de escopo deste bloco).
- **Decisão — modelo de dados:**
  - Nova tabela `installment_plans` (migration `0004_deep_machine_man.sql`, gerada e revisada, **não aplicada**): `id`/`household_id`/`description`/`category_id`/`total_amount`/`installment_count`/`first_reference_month`/`due_day`/`created_by_user_id`/`created_at`, seguindo em tudo as convenções já estabelecidas do schema — `bigint unsigned` para todo campo numérico (nunca `int`), `decimal(13,2)` para dinheiro (nunca `float`/`double`), FK composta `(category_id, household_id) → categories(id, household_id)` com `ON DELETE RESTRICT` (mesmo padrão de `financial_entries_category_household_fk`), `unique(id, household_id)` como alvo de FK composta (mesmo padrão de `categories`/`monthly_periods`), e três `CHECK` (`total_amount > 0`, `installment_count >= 2`, `due_day` entre 1 e 31). `due_day` é `NOT NULL` — reafirma a correção feita na revisão do Bloco 02 (nunca opcional). Deliberadamente **sem FK para `monthly_periods`**: `first_reference_month` é uma data solta, não uma competência garantida existir no momento da criação do plano (ver Bloco 01/02).
  - `financial_entries` ganha duas colunas nullable — `installment_plan_id`/`installment_number` — nunca `installment_total` nem duplicação de `total_amount`/`installment_count` (esses campos vivem exclusivamente em `installment_plans`; `GeneratedInstallment`, do Bloco 02, permanece um tipo intermediário de domínio, nunca substituto de `FinancialEntry`). Coerência garantida por `CHECK financial_entries_installment_coherence_check` (ambas nulas ou ambas preenchidas, nunca uma sem a outra) e por um índice único composto `(installment_plan_id, installment_number)` (impede duas parcelas com o mesmo número no mesmo plano; NULLs nunca colidem entre si num índice único do MySQL, então lançamentos comuns nunca são bloqueados).
  - FK composta `financial_entries_installment_plan_household_fk` `(installment_plan_id, household_id) → installment_plans(id, household_id)`, **`ON DELETE RESTRICT`, nunca `CASCADE`** — reafirma a decisão do Bloco 01 de que excluir um plano nunca apaga automaticamente as parcelas já lançadas (não existe, aliás, nenhuma rota de exclusão de `InstallmentPlan` nesta versão — a porta é deliberadamente imutável, sem `update()`/`remove()`). `SET NULL` foi descartado, não por preferência mas por impossibilidade técnica: o MySQL 8 proíbe (erro `3823`, `ER_CHECK_CONSTRAINT_CLAUSE_USING_FK_REFER_ACTION_COLUMN`) uma coluna alvo de `SET NULL`/`CASCADE` em FK ser também referenciada por uma `CHECK` — e `installment_plan_id` é referenciado pela `CHECK` de coerência acima. Mesma restrição, mesma solução já usada por `financial_entries_responsible_member_household_fk` (DT-09).
  - `InstallmentPlanRepository` (porta nova): `findById`, `findByHousehold`, `create()` — sem `update()`/`remove()` (imutabilidade de produto, não limitação técnica). `DrizzleInstallmentPlanRepository.create()` segue exatamente o padrão nativo corrigido em DT-15 (`INSERT` sem `id`, valor real lido de `ResultSetHeader.insertId`) — é a primeira tabela nova desde DT-15, e nasce já sem a dívida técnica que ele descreve: nunca teve `nextId()`, nunca lê `information_schema`. `InMemoryInstallmentPlanRepository` replica a mesma semântica de isolamento por household e imutabilidade, sem tentar reproduzir os detalhes do `AUTO_INCREMENT` real do MySQL.
  - Nenhuma tabela nova foi conectada a `createDrizzleRepositories`/`DrizzleRepositories`/`HttpAppRepositories`/`build-test-app.ts` — essa integração (DI) e qualquer serviço de orquestração transacional (`CreateInstallmentPurchase`, RS-01) ficam reservados para o Bloco 04, deliberadamente fora de escopo aqui.
- **Reavaliação formal do risco de DT-15 para `DrizzleFinancialEntryRepository` no contexto do Bloco 04 (pedido explícito do proprietário neste bloco):**
  - **Conclusão: B — risco real, não apenas teórico, especificamente para o caso de uso que o Bloco 04 pretende implementar (criar N `FinancialEntry` — uma por parcela — a partir de um único `InstallmentPlan`).**
  - **Mecanismo:** `DrizzleFinancialEntryRepository.nextId()` (`drizzle-financial-entry-repository.ts:132-145`) usa exatamente o padrão que DT-15 já documentou como defeituoso: `SELECT AUTO_INCREMENT FROM information_schema.TABLES WHERE TABLE_NAME = 'financial_entries'`. Essa leitura não reflete de forma confiável um `INSERT` recém-concluído no mesmo processo — é a mesma causa-raiz já diagnosticada e corrigida para `auth_sessions`. Um fluxo do tipo `for (parcela de 1..N) { id = await nextId(); await save({ id, ... }) }` chama `nextId()` de novo logo após cada `INSERT`, exatamente o padrão sequencial em que a metadata consultada já se mostrou capaz de não avançar entre chamadas — o segundo `nextId()` pode devolver o mesmo `id` já usado pela primeira parcela.
  - **Consequência silenciosa, não apenas um erro visível:** ao contrário de uma simples colisão de `PRIMARY KEY` (que falharia alto, com `ER_DUP_ENTRY`), `save()` verifica primeiro se o `id` já existe (`existing.length === 0`) — se `nextId()` devolver um valor repetido, `save()` da segunda parcela entra no ramo de `UPDATE` (mesmo household, então passa também pela checagem de `HouseholdScopeViolationError`) e **sobrescreve silenciosamente a primeira parcela já persistida**, sem lançar nenhum erro. É o mesmo modo de falha já comprovado para `auth_sessions` antes da correção de DT-15, agora aplicado a um cenário sequencial de um único household (não exige dois usuários concorrentes — o próprio Bloco 04, chamando `nextId()`/`save()` em loop dentro de uma mesma requisição, é suficiente para reproduzir o problema).
  - **Por que isto muda a avaliação de risco já registrada em DT-15:** a nota de dívida técnica original (DT-15, penúltimo parágrafo) julgou o risco para `financial_entries` "menor que o de `auth_sessions`" citando que criar uma movimentação é "uma ação deliberada do usuário, não uma consequência automática de todo carregamento de página". Essa comparação continua válida para o uso *atual* do repositório (uma movimentação por vez), mas **não se estende** ao uso que o Bloco 04 pretende introduzir — múltiplas chamadas de `nextId()`/`save()` em sequência rápida, dentro da mesma requisição, para o mesmo household. O cenário deixa de ser "dois usuários abrindo o app ao mesmo tempo" (raro) e passa a ser "todo parcelamento com 2+ parcelas" (o caso comum da própria funcionalidade que o Bloco 04 existe para entregar).
  - **Mudança mínima necessária (não implementada neste bloco, por instrução explícita do proprietário):** espelhar exatamente a solução já aplicada a `auth_sessions` em DT-15 — adicionar um método `create(entry: Omit<FinancialEntry, 'id'>): Promise<FinancialEntry>` a `FinancialEntryRepository`/`DrizzleFinancialEntryRepository`/`InMemoryFinancialEntryRepository`, que insere sem `id` e lê o valor real de `ResultSetHeader.insertId`, **sem remover nem alterar** `nextId()`/`save()` — que continuam em uso por todo o resto da aplicação (edição, cancelamento, reativação, exclusão de movimentações avulsas). O Bloco 04 usaria exclusivamente esse novo `create()` no laço de geração de parcelas; nenhum outro fluxo muda de comportamento.
  - **Impacto no Bloco 03 (este bloco):** nenhum — nenhuma linha de `drizzle-financial-entry-repository.ts` foi tocada; a tabela/repositório novos deste bloco (`installment_plans`) já nasceram usando `insertId` nativo, sem essa dívida.
  - **Impacto no Bloco 04:** este achado deve ser tratado **antes** de desenhar o serviço de orquestração transacional (RS-01) — sem o `create()` dedicado, qualquer implementação ingênua do laço "uma parcela por vez" tem alta probabilidade de sobrescrever parcelas silenciosamente já no primeiro parcelamento de teste com 3+ parcelas. Recomendação: tratar a adição do `create()` como uma correção curta e isolada no início do Bloco 04 (ou como um Bloco 03-B dedicado, a critério do proprietário), antes de qualquer código de orquestração/transação.
- **Testado:** mapper (`installment-plan-mapper.test.ts`, round-trip domínio↔persistência, conversão de dinheiro e `createdAt`); repositório Drizzle via `FakeDrizzleDb` (`drizzle-installment-plan-repository.test.ts` — `create()` sempre sem `id` fornecido, ids distintos em chamadas sequenciais e entre households, nunca um `UPDATE` disfarçado, propagação de `PersistenceError`, e um teste estático que garante que o código-fonte real nunca menciona `information_schema`/`nextId`/`MAX(id)`, mesmo padrão de DT-15); repositório em memória (`in-memory-installment-plan-repository.test.ts` — isolamento por household, `reset()`); asserções estáticas de schema (`schema.test.ts` — tipos de coluna, `CHECK`s, FKs simples e compostas, ausência de FK para `monthly_periods`, nullability e ausência de `installment_total`/`total_amount`/`installment_count` em `financial_entries`). Duas correções mínimas de compatibilidade em fixtures de teste pré-existentes (`buildRow()` em `drizzle-financial-entry-repository.test.ts` e `financial-entry-mapper.test.ts`, que passaram a exigir `installmentPlanId`/`installmentNumber` como chaves presentes por causa de `$inferSelect`) — nenhuma mudança em código de produção foi necessária (`$inferInsert` trata colunas nullable sem default como chaves opcionais). ### DT-16 — Exclusão real de movimentações substitui o cancelamento como ação destrutiva da interface (elegibilidade mais ampla que o cancelamento)

- **Data:** 2026-08-06
- **Contexto:** o cancelamento (`cancelFinancialEntry`, `planned`/`pending` → `cancelled`) nunca removia o registro — apenas mudava seu status, mantendo-o visível e computável no histórico. O usuário pediu uma ação que remova de fato um lançamento incorreto/duplicado, sem perder a capacidade já existente de consultar/reativar lançamentos já cancelados no passado.
- **Revisão dentro do mesmo bloco:** a primeira versão desta decisão fazia `assertFinancialEntryDeletable` herdar exatamente as mesmas precondições de `cancelFinancialEntry` (só `planned`/`pending`). Em revisão antes da aprovação, o usuário apontou que isso obrigava um lançamento `realized` por engano a passar por um fluxo de estorno só para depois ser excluído — sem necessidade real, já que a competência aberta já é a mesma garantia usada para qualquer outra correção. A regra final ampliou a elegibilidade para incluir `realized`, mantendo `cancelled` de fora (única exceção, com justificativa própria abaixo). Nenhum código chegou a ser commitado com a versão anterior — esta é a única versão registrada.
- **Decisão:**
  - **Exclusão é remoção real de linha, nunca soft delete.** Nova operação `FinancialEntryRepository.remove(id, householdId)`, implementada nos dois repositórios (Drizzle: `DELETE FROM financial_entries WHERE id = ? AND household_id = ?`; memória: remoção do `Map` só se o `householdId` bater) — mais estrita que o precedente de `CategoryBudgetRepository.remove(id)` (Bloco 18), que não escopa por household na cláusula `WHERE`.
  - **Elegibilidade: competência aberta é a única exigência de contexto; entre os status, só `cancelled` fica de fora.** `assertFinancialEntryDeletable(entry, period)` reusa a mesma regra de competência de `cancelFinancialEntry` (`assertPeriodAllowsEntryChanges` sem `allowReviewAdjustment` — bloqueia `closed` e `review`), mas **não** reusa o conjunto de status: `planned`, `pending` e `realized` são todos elegíveis; só `cancelled` é rejeitado (`InvalidStatusTransitionError`). Continua sendo um validador puro (lança ou retorna `void`), nunca uma função de transição — exclusão não é um novo `FinancialEntryStatus` e não compõe `FINANCIAL_ENTRY_ALLOWED_TRANSITIONS`.
  - **Por que `realized` é elegível (diferente do cancelamento):** um lançamento marcado como realizado por engano é o mesmo tipo de erro de cadastro que um `planned`/`pending` errado — a única proteção que faz sentido é a mesma já aplicada a toda alteração: a competência estar aberta. Exigir um estorno prévio (`realized` → `pending`) só para depois excluir seria um passo extra sem valor, já que a exclusão não é uma correção de valor (isso já é o papel da edição/estorno) — é a remoção de um registro que não deveria existir.
  - **Por que `cancelled` continua de fora:** um registro `cancelled` já é o resultado de uma ação destrutiva anterior (o cancelamento) — "Reativar" (`cancelled` → `planned`) é o único caminho de volta desenhado para esse estado, e permitir excluir diretamente um `cancelled` misturaria dois caminhos destrutivos para o mesmo registro sem necessidade (quem quiser excluir um lançamento cancelado pode reativá-lo primeiro).
  - **`cancelled` como status, `cancelFinancialEntry`, `CancelFinancialEntryService`, a rota `POST .../cancel` e a reativação (`reactivateFinancialEntry`/`POST .../reopen`) permanecem intactos e funcionais** — nenhuma migration, nenhuma remoção de enum. Só o caminho de UI que **inicia** um novo cancelamento foi removido (`CancelEntryDialog.tsx` apagado, botão "Cancelar" da lista de movimentações substituído por "Excluir"). Registros já `cancelled` continuam exibidos e reativáveis normalmente.
  - **Frontend reaproveita a infraestrutura de diálogo/mutação já existente** (`EntryDialog`, `useMutationDialog`, classe `fh-entry-form__primary--danger`) — nenhum padrão visual novo. Nova ação `DELETE_ENTRY` no `FinanceAction` segue o mesmo fluxo de toda outra mutação em `FinanceProvider` (chama a API, recarrega `listEntries()`, despacha `MUTATION_SUCCESS`) — Dashboard/Comparativo/Planejamento/Histórico refletem a exclusão automaticamente, sem nenhuma invalidação cross-page dedicada.
  - **Botão "Nova movimentação" removido do `DashboardHeader`** (CTA desabilitado, redundante com a navegação já oferecida pela Sidebar) — decisão de simplificação de UI empacotada no mesmo bloco a pedido do usuário, sem relação técnica com a exclusão.
- **Por que não soft delete:** um status `deleted` exigiria filtrar esse status em toda leitura existente (`findByHousehold`, `findByPeriod`, view-models de todas as páginas) — superfície de erro maior que uma remoção real, para um caso de uso ("eu me enganei, quero apagar") que não tem valor de auditoria retroativa comparável ao de um cancelamento (que já preserva o registro).
- **Testado:** domínio (`assertFinancialEntryDeletable`, 8 casos, incluindo `realized` permitido em competência aberta e bloqueado em competência fechada), serviço de aplicação (`DeleteFinancialEntryService`, 7 casos incluindo exclusão de `realized`, rejeição de `cancelled`, rejeição por competência fechada com `realized`, e isolamento por household), repositório Drizzle via `FakeDrizzleDb` (3 casos), rota HTTP (11 casos: sucesso `planned`/`pending`/`realized`, 404 inexistente, 404 outro household — inclusive `realized` de outro household —, 401 sem sessão, 409 competência fechada para `planned` e para `realized`, 409 status `cancelled`, 503 erro sanitizado), reducer de teste do frontend e sincronização com dashboard/comparativo/planejamento/histórico (cada um com um caso dedicado a excluir uma movimentação `realized` e confirmar o recálculo dos totais), página `FinancialEntriesPage` (abrir/fechar diálogo, Escape, confirmar — inclusive para `realized` —, erro mantém o lançamento, `cancelled` nunca oferece "Excluir").
- **Consequências:** `FinancialEntryRowViewModel.canCancel` renomeado para `canDelete` (`entry.status !== 'cancelled'`) — nenhuma checagem de competência no view-model, mesmo padrão já usado por `canMarkPending`/`canRealize`/etc. (rejeição por competência é sempre responsabilidade do backend, superfície ao usuário via `state.actionError`).

### DT-15 — Geração do id de `auth_sessions`: `AUTO_INCREMENT` nativo, nunca calculado em código

- **Data:** 2026-08-06
- **Contexto:** durante a validação funcional manual do Bloco 19, o login parou de avançar ao Dashboard depois do primeiro uso real — a API retornava 200 no login e definia o cookie, mas toda validação de sessão seguinte falhava (401). A investigação (reprodução isolada, sem navegador nem proxy, direto na API) revelou uma cadeia de duas causas em `DrizzleAuthSessionRepository`, corrigidas em duas etapas dentro do mesmo dia:
  1. **Causa original:** `nextId()` lia `information_schema.TABLES.AUTO_INCREMENT` — uma metadata do InnoDB que não avança de forma confiável quando o `id` é sempre atribuído explicitamente pelo código (nunca deixado para o auto-increment real). Na prática, `nextId()` passou a devolver sempre o mesmo valor já usado pela primeira sessão criada; todo login seguinte colidia nesse `id` e entrava no ramo de `UPDATE` de um único método `save()` (insere ou atualiza dependendo da existência prévia), que não regravava `token_hash` — a sessão no banco nunca voltava a corresponder ao cookie emitido.
  2. **Correção intermediária rejeitada:** ler `MAX(id) + 1` da própria tabela (em vez de `information_schema`) e regravar `token_hash` também no `UPDATE` resolveu o sintoma observado, mas manteve uma condição de corrida real: dois logins simultâneos ainda podiam calcular o mesmo próximo `id` antes de qualquer `INSERT` acontecer. Para o mesmo usuário, um login sobrescreveria silenciosamente o `token_hash` do outro (invalidando a sessão mais antiga sem aviso, já que "regravar token_hash no UPDATE" não elimina a colisão — só transforma uma falha visível em invalidação silenciosa); para usuários diferentes, o segundo `INSERT` falharia por `ER_DUP_ENTRY`. Esse risco é real nesta aplicação — duas pessoas do mesmo household abrindo o app perto uma da outra é o caso comum, não uma borda rara.
- **Decisão final:** o `id` de `auth_sessions` nunca é calculado em código. A porta `AuthSessionRepository` foi dividida em `create(session: NewAuthSession)` (sempre insere uma linha nova, sem `id` — o `AUTO_INCREMENT` nativo do MySQL gera o valor, lido de volta via `ResultSetHeader.insertId`) e `update(session: AuthSession)` (só existe para tocar uma sessão já existente — revogação, `lastUsedAt` — e nunca altera `token_hash`, que passa a pertencer exclusivamente ao momento da criação). `nextId()` foi removido inteiramente da porta e da implementação Drizzle; não há mais nenhuma leitura de `information_schema` nem cálculo de `MAX(id)` para esta tabela.
- **Por que `MAX(id) + 1` foi rejeitado como solução definitiva:** qualquer leitura-antes-de-escrever calculada em código (seja via metadata do InnoDB, seja via `MAX(id)` da própria tabela) tem uma janela entre a leitura e o `INSERT` em que outra transação pode observar o mesmo valor — a única forma de eliminar essa janela é delegar a geração do id inteiramente ao mecanismo atômico do próprio banco (`AUTO_INCREMENT`), nunca reimplementá-lo em código de aplicação.
- **Testado:** testes unitários do repositório (`FakeDrizzleDb`) cobrindo criação sem `id` fornecido, dois `create()` sequenciais com `id`s distintos, `update()` nunca alterando `token_hash`, `update()` rejeitando id inexistente/de outro usuário, e verificação estática de que o código-fonte real (fora de comentários) nunca menciona `information_schema`/`MAX(id)`/`nextId`. Testes de serviço (`auth-services.test.ts`) cobrindo duas sessões do mesmo usuário simultaneamente válidas, logout seletivo sem afetar a outra sessão, e dois usuários diferentes sem colisão. `db-smoke-auth-sessions.ts` (transação real contra `finanhouse_dev`, sempre revertida) estendido para o mesmo cenário fim a fim. Validado também no navegador real, com dois `BrowserContext` do Playwright representando duas sessões simultâneas da mesma conta — ambas funcionaram de forma totalmente independente, incluindo logout seletivo.
- **Consequências:** `toPersistenceAuthSession` (mapper) foi removido — ficou sem uso depois que `create()`/`update()` passaram a montar seus próprios objetos de persistência com escopo de campos diferente (criação nunca inclui `id`; atualização nunca inclui `token_hash`). `InMemoryAuthSessionRepository` foi ajustado para o mesmo contrato `create()`/`update()` (seu contador interno já não tinha o bug, mas a interface precisava ficar consistente). O harness de teste HTTP (`build-test-app.ts`, autenticação automática de testes) também foi atualizado para `create()`.
- **Dívida técnica formal (P2) registrada:** `drizzle-category-budget-repository.ts`, `drizzle-financial-entry-repository.ts` e `drizzle-monthly-period-repository.ts` usam exatamente o mesmo padrão vulnerável (`nextId()` via `information_schema.TABLES.AUTO_INCREMENT` + `save()` único insere-ou-atualiza) — os próprios comentários originais desses arquivos já reconheciam o risco e apontavam a mesma solução (`ResultSetHeader.insertId`) como a alternativa correta para um cenário com escritores concorrentes. Não foram corrigidos neste bloco: o risco de colisão é menor que o de `auth_sessions` (criação de movimentação/competência/limite é uma ação deliberada do usuário, não uma consequência automática de todo carregamento de página como o login é), mas não é nulo — `ensurePeriod` roda a cada carga do Dashboard e pode colidir se os dois membros do household abrirem o app quase ao mesmo tempo no início de um mês novo. Corrigir os três exigiria repetir o mesmo padrão de refatoração (porta, implementação Drizzle, repositório em memória, serviços de aplicação, testes) em escopo comparável ao desta correção — não é uma mudança pequena o suficiente para entrar de forma segura neste bloco. Sugestão: bloco futuro dedicado, aplicando exatamente a mesma estratégia (`create()`/`update()` separados, `insertId` nativo) aos três repositórios.
- **Status:** a dívida técnica P2 acima foi **resolvida em 2026-08-20** pela DT-18 (rodada de correção/hardening pré-Bloco 04) — os três repositórios usam agora `create()`/`update()` com `insertId` nativo, sem nenhum `nextId()`/leitura de `information_schema` remanescente.

### DT-14 — Autenticação real e sessão doméstica

- **Data:** 2026-08-04
- **Contexto:** desde o Bloco 12 (DT-08), `createHttpApp` recusa `runtimeMode: 'production'` justamente por não existir autenticação real — `createdByUserId`/`closedByUserId` vinham diretamente do corpo da requisição (qualquer cliente podia se passar por qualquer usuário do household) e o frontend resolvia `householdId` de uma variável de ambiente local (`VITE_FINANHOUSE_HOUSEHOLD_ID`), não de uma identidade autenticada. O household estrutural (Bloco 17) já tem exatamente dois usuários reais — não há cadastro a construir, só login para quem já existe.
- **Decisão:**
  - **Sem cadastro público.** Só os dois usuários já vinculados ao household (bootstrap do Bloco 17) podem autenticar — nenhuma rota cria usuário novo.
  - **Senha:** hash Argon2id via `@node-rs/argon2` (bindings nativos pré-compilados via napi-rs, sem toolchain de build necessário neste ambiente Windows — validado por instalação e teste real). Nenhuma implementação própria de criptografia. `users.password_hash` nullable até a configuração inicial (autorização separada, seção 18 do prompt); comparação sempre via `verify()` da própria biblioteca (resistente a timing attack pela natureza do algoritmo, nunca `===` em texto puro).
  - **Sessão:** token opaco de 256 bits gerado por `crypto.randomBytes` (CSPRNG), nunca um JWT — o banco nunca vê o token bruto, apenas seu hash SHA-256 (`auth_sessions.token_hash`, único). SHA-256 (rápido) é intencionalmente diferente de Argon2id (lento): o token já tem entropia alta o bastante (256 bits) para não precisar de uma função de derivação cara — Argon2id existe para proteger segredos de baixa entropia (senhas humanas), não tokens aleatórios.
  - **Cookie:** o token bruto só existe em um cookie `HttpOnly`, `SameSite=Lax`, `Secure` fora de `development` — nunca acessível a JavaScript, nunca em `localStorage`/`sessionStorage` (reafirma DT-12: nenhuma persistência local de dado sensível).
  - **Tabela nova `auth_sessions`:** `user_id`/`household_id` (FKs simples para `users`/`households`, `RESTRICT`), `token_hash` único, `expires_at`, `revoked_at` nullable, `created_at`, `last_used_at` nullable. Vínculo do usuário com o household (ativo ou não) é validado na aplicação no momento do login, não por FK — mesmo raciocínio de DT-13 (status validado fora do banco).
  - **`createdByUserId`/`closedByUserId` passam a vir exclusivamente da sessão** (`request.authSession.userId`) — removidos dos schemas de corpo das rotas de `entries`/`periods`; um cliente não consegue mais forjar outro usuário.
  - **`householdId` do frontend vem da sessão** (`GET /api/v1/auth/session`), não mais de `VITE_FINANHOUSE_HOUSEHOLD_ID` — a variável é removida do frontend real (permanece, se necessário, só em scripts server-side).
  - Todas as rotas financeiras (`categories`, `members`, `periods`, `entries`, `budgets`) passam a exigir sessão válida via `preHandler` — sessão ausente/expirada/revogada retorna 401; o `householdId` da URL precisa bater com o da sessão (senão 404, mesmo padrão de "recurso de outro household nunca é distinguível de inexistente").
  - CORS ganha `Access-Control-Allow-Credentials: true`, mantendo a mesma lista fechada de origens locais (nunca wildcard) — necessário para o navegador enviar o cookie `HttpOnly` em `fetch(..., { credentials: 'include' })`.
  - Autenticação continua sem tornar a API apta para produção: `createHttpApp` ainda recusa `runtimeMode: 'production'` (autenticação real é necessária, mas não suficiente — CORS/bind ainda são estritamente locais).
- **Fora de escopo, registrado como dívida futura:** cadastro público, recuperação de senha, MFA, OAuth, permissões granulares além de `owner`/`member`, limpeza periódica de sessões expiradas, deploy seguro.
- **Consequências:** repositório `DrizzleAuthSessionRepository` segue o mesmo padrão "nunca upsert" de `DrizzleCategoryBudgetRepository` (DT-13). Um `UserRepository` mínimo (somente leitura, `findByEmail`/`findById`) e uma extensão de `HouseholdMemberRepository` (`findByUserId`) foram criados — nenhuma modelagem de domínio em `@finanhouse/domain` para `User`, mesma decisão de DT-10 (não há regra de negócio financeira sobre usuários, apenas identidade técnica). Auditoria dedicada (`db-audit-auth-sessions.ts`) segue o padrão de DT-13 (banco não-vazio pós-bootstrap). Script de configuração de senha iniciais é permanente e exige autorização separada da migration (seções 17/18 do prompt do Bloco 19), nunca executado automaticamente. Duas dependências oficiais do ecossistema Fastify (já na mesma major version 5 já usada pelo projeto) foram adicionadas: `@fastify/cookie` (parsing/serialização do cookie de sessão) e `@fastify/rate-limit` (limite de tentativas de login) — nenhuma implementação própria de nenhuma das duas, mesmo raciocínio de "não reinventar primitiva de segurança" do Argon2id.

- **Consequências:** `FinanceDemoProvider`/`financeDemoReducer`/`data/dashboard-fixtures.ts` foram removidos do runtime; a mesma lógica de transição (delegando sempre a `@finanhouse/domain`) foi portada para `apps/web/src/state/test-support/` como infraestrutura exclusiva de teste (`FinanceTestProvider`), nunca importada por `main.tsx`. Um script de bootstrap estrutural (`apps/api/scripts/db-bootstrap-household.ts`) cria o household/membros/categorias iniciais em `finanhouse_dev` — operação permanente, distinta de qualquer smoke-test sintético com rollback (Blocos 13/14/16).

### DT-11 — API HTTP financeira local com injeção de dependência

- **Data:** 2026-08-01
- **Contexto:** o Bloco 14 (DT-10) implementou os repositórios Drizzle reais, mas nenhuma camada HTTP conectava os serviços de aplicação já existentes (`apps/api/src/application/services/`) a uma API real — a API tinha apenas `GET /health` sobre `node:http` puro, sem framework, sem roteador, sem parsing/validação de corpo. Nenhum framework HTTP estava instalado no projeto.
- **Decisão:** adotado **Fastify 5.11.0** como camada HTTP (`apps/api/src/http/`), com uma fábrica pura `createHttpApp({ repositories, logger, runtimeMode, readiness })` (`app.ts`) separada do bootstrap runtime (`server.ts`, que lê `.env.local`, cria o pool real e efetivamente escuta uma porta). A fábrica:
  - recebe as quatro portas já existentes (`FinancialEntryRepository`, `MonthlyPeriodRepository`, `CategoryRepository`, `HouseholdMemberRepository`) por injeção — nunca instancia repositório concreto, nunca cria pool, nunca lê `.env.local`;
  - **recusa `runtimeMode: 'production'`** de forma explícita e testada — a API não implementa autenticação real neste bloco, e executá-la em produção sem controle de acesso exporia dados financeiros;
  - expõe 21 rotas sob `/api/v1/households/:householdId/...` (`categories`, `members`, `periods` com 4 ações de transição, `entries` com 6 ações de transição), todas reaproveitando os serviços de aplicação já existentes — nenhuma regra de domínio duplicada em handler;
  - traduz erros via um handler central que mapeia toda a hierarquia de `DomainError` (404/409/422 conforme o caso) e `PersistenceError` (409/422/503/500, DT-10), preservando o desembrulhamento de `DrizzleQueryError.cause`;
  - nunca expõe a coluna auxiliar `responsible_member_household_id` (DT-09) nos DTOs de resposta;
  - recebe dinheiro exclusivamente como string decimal (`"10.00"`, nunca `number` JSON) e converte via `parseMoney`/`formatMoney` (`@finanhouse/domain`) — nunca `parseFloat`;
  - exige bind estritamente local (`127.0.0.1`, nunca configurável, nunca `0.0.0.0`) e CORS restrito a `http://127.0.0.1:5173`/`http://localhost:5173` (nunca wildcard).
- **Correção real encontrada durante a implementação:** o Fastify usa `removeAdditional: true` por padrão no AJV — removeria silenciosamente campos desconhecidos do corpo (incluindo um `householdId` concorrente enviado no corpo, tentando contornar o escopo da URL) em vez de rejeitá-los. Corrigido com `ajv.customOptions.removeAdditional: false` na criação da instância Fastify, validado por testes reais via `app.inject()` confirmando rejeição (400) e ausência de efeito colateral (nenhum dado salvo).
- **Motivos:** Fastify oferece validação de schema via AJV nativamente (sem dependência extra para validação estrutural), suporta injeção de dependência limpa via fábrica, e `app.inject()` permite testar rotas reais sem abrir socket de rede nem conexão de banco; manter a fábrica pura separada do bootstrap runtime permite testar toda a superfície HTTP com repositórios em memória, sem qualquer efeito colateral.
- **Alternativas consideradas:** Express — descartado por exigir bibliotecas adicionais para validação de schema equivalente; manter `node:http` puro com roteamento manual — descartado por não escalar para 21 rotas com validação estruturada sem reimplementar, na prática, um roteador e um validador.
- **Consequências:** RF-05 avança (infraestrutura + schema + repositórios + API HTTP v1 concluídos), mas não é declarado concluído — integração do frontend com a API e autenticação real continuam pendentes; o modo demonstrativo do frontend foi preservado sem alteração; nenhuma rota HTTP deste bloco é acessível publicamente (bind local, sem autenticação) — não deve ser apresentada como pronta para exposição externa em nenhum ambiente até que a autenticação real exista.
- **Status:** Vigente

### DT-10 — Repositórios Drizzle reais

- **Data:** 2026-07-31
- **Contexto:** desde DT-08/DT-09, o schema estava aplicado em `finanhouse_dev`, mas a aplicação continuava lendo/escrevendo apenas repositórios em memória (`apps/api/src/infrastructure/repositories/memory/`) — nenhum adaptador real conectava as portas de repositório (`apps/api/src/application/ports/`) ao banco. O Bloco 14 implementou esses adaptadores.
- **Decisão:** criados `DrizzleFinancialEntryRepository`, `DrizzleMonthlyPeriodRepository`, `DrizzleCategoryRepository`, `DrizzleHouseholdMemberRepository` e a fábrica `createDrizzleRepositories(db)` em `apps/api/src/infrastructure/repositories/drizzle/`, implementando exatamente as quatro portas já existentes — nenhuma porta nova foi criada. Não existe porta/repositório para `users`/`households` (nenhum serviço de aplicação hoje precisa persisti-los diretamente) — lacuna registrada, não preenchida com arquitetura paralela. Pontos centrais:
  - **Injeção de dependência:** cada repositório recebe a instância `DrizzleDb` (ou uma `transaction`, já que ambas compartilham o mesmo tipo base `MySqlDatabase`) pelo construtor — nenhum singleton global, nenhuma conexão aberta durante a importação dos módulos (verificado por teste estático).
  - **Mapeamento de dinheiro:** colunas `DECIMAL(13,2)` chegam como `string` do driver; `parseMoney`/`formatMoney` (`@finanhouse/domain`) cruzam essa fronteira nos dois sentidos — nunca `Number`/`parseFloat` como representação intermediária.
  - **Coluna auxiliar do membro responsável:** `responsible_member_household_id` (DT-09) é derivada internamente em `toPersistenceFinancialEntry` (espelha `household_id` só quando há responsável) e nunca é aceita como entrada nem exposta ao domínio — confirmado por teste e pelo smoke transacional.
  - **Enums:** valores lidos do banco são validados contra as constantes de domínio (`assertKnownValue`) antes de virar um valor tipado — nunca um `as` irrestrito; um valor inesperado lança `UnexpectedPersistedValueError` de forma controlada.
  - **Escopo obrigatório por household nas leituras:** `findByHousehold`/`findByHouseholdAndReferenceMonth` sempre filtram por `household_id` no `WHERE`, testado com dados de dois households simultâneos (nunca vazamento cruzado). `findById(id)` continua sem escopo de household — comportamento herdado da porta já existente (idêntico ao repositório em memória), não alterado neste bloco.
  - **Escopo obrigatório por household nas escritas — corrigido durante o checkpoint:** a primeira versão de `save()` usava `INSERT ... ON DUPLICATE KEY UPDATE`. Revisão do proprietário (antes de qualquer escrita real) apontou que, no MySQL, um upsert pode ser acionado por **qualquer** índice único (não só a chave primária) e a atualização resultante não fica limitada por `household_id` — poderia sobrescrever silenciosamente um registro de outro household em caso de colisão de `id`, ou mascarar como atualização um conflito de unicidade legítimo (ex.: `monthly_periods (household_id, reference_month)`). Corrigido para: `SELECT household_id` do registro existente (se houver) → se não existe, `INSERT` simples (nunca upsert); se existe e o `household_id` diverge do informado, lança `HouseholdScopeViolationError` explicitamente em código (nunca permite mover um registro entre households); se existe e o `household_id` confere, `UPDATE ... WHERE id = ? AND household_id = ?` (condição composta), com `SET` que nunca inclui `id`/`household_id`.
  - **Tradução de erros:** `persistence-errors.ts` traduz erros de driver para uma hierarquia sanitizada (`PersistenceError` e subclasses, incluindo `HouseholdScopeViolationError` para violação das FKs/CHECK compostas), reconhecendo pelo `code` estável do mysql2, nunca pela mensagem bruta; reaproveita `categorizeConnectionError` (relocado de `apps/api/scripts/lib/` para `apps/api/src/db/sanitize-error.ts`, já que `src/` não pode importar de `scripts/`).
  - **`nextId()` via `information_schema`:** mantido, mas com risco de concorrência sob múltiplos escritores explicitamente documentado no código — não deve ser tratado como estratégia definitiva para um cenário de produção com concorrência real (a alternativa correta nesse caso seria confiar no `insertId` nativo do `INSERT` e reestruturar a porta para não exigir um `id` pré-conhecido).
- **Bug real encontrado e corrigido durante o smoke-test transacional:** a primeira execução autorizada do smoke-test falhou no cenário "responsável de outro household deve ser rejeitado" — o erro real do MySQL (violação da FK composta) não estava sendo reconhecido como `HouseholdScopeViolationError`. Diagnóstico (autorizado explicitamente pelo proprietário, mesma exceção pontual de DT-09 para erros de schema/constraint sem credenciais) revelou a causa: o Drizzle envolve todo erro de query real em `DrizzleQueryError`, cuja própria `message` é só `"Failed query: ... params: ..."` — o erro do driver mysql2, com `code`/`sqlMessage`, fica um nível abaixo, em `.cause`. `translatePersistenceError` só inspecionava o erro de nível superior. Corrigido com uma função `unwrapDriverError` que desembrulha um nível de `.cause` quando o erro de topo não tem `code` mas sua causa tem — com 4 testes de regressão cobrindo esse formato. Depois da correção, o smoke-test foi reexecutado (segunda autorização explícita) e aprovado em todos os passos.
- **Smoke-test transacional:** `apps/api/scripts/db-smoke-repositories.ts` (`npm run db:smoke:repositories`, exige `CONFIRM_REPOSITORY_SMOKE=true`) cria dados sintéticos (domínio `.invalid`) dentro de uma única `db.transaction()`, exercita os repositórios reais (leitura após escrita, isolamento por household, membro responsável do mesmo e de outro household, atualização), e força um `SmokeRollbackSignal` ao final — nunca um `COMMIT`. Confirmado por auditoria somente leitura antes/depois: seis tabelas vazias, duas migrations, nenhum dado residual.
- **Motivos:** conectar a arquitetura de portas/serviços já existente ao schema real é pré-requisito de RF-05; preservar as portas exatamente como estão evita uma segunda arquitetura paralela; recusar upsert evita uma classe inteira de bugs de isolamento entre households que só se manifestaria em produção, com dados reais, sob colisão de índice único.
- **Alternativas consideradas:** manter o upsert e confiar apenas na FK/CHECK do banco para impedir cruzamento de household — rejeitada porque a FK composta do membro responsável não cobre `id`/`household_id` da própria `financial_entries`/`monthly_periods` (só cobre a referência ao membro), deixando uma lacuna real de isolamento nas próprias tabelas graváveis; usar `information_schema` apenas como estratégia definitiva de geração de ID mesmo sob concorrência real — rejeitada e documentada como limitação conhecida, não resolvida neste bloco (fora de escopo: aplicação de um único usuário/household).
- **Consequências:** RF-05 avança (infraestrutura + schema + repositórios Drizzle reais concluídos) mas **não é declarado concluído** — endpoints de API HTTP e integração do frontend com a API continuam pendentes; nenhuma rota HTTP foi criada neste bloco; o modo demonstrativo do frontend (`Docs/02_architecture/estado_temporario_frontend.md`) foi preservado sem alteração; `users`/`households` sem porta de repositório é uma lacuna registrada para um bloco futuro, não uma decisão definitiva de nunca implementá-los.
- **Status:** Vigente

### DT-09 — Integridade composta do membro responsável

- **Data:** 2026-07-31
- **Contexto:** desde o Bloco 03, `financial_entries.responsible_member_id` tinha apenas uma FK simples para `household_members.id` — o MySQL não garantia que o membro responsável pertencesse ao mesmo household da movimentação; essa consistência dependia inteiramente da camada de serviço (registrada como pendência P2 nos feedbacks dos Blocos 03 e 04). Uma FK composta direta `(responsible_member_id, household_id) → household_members(id, household_id)` não era possível com `ON DELETE SET NULL`, porque `household_id` é `NOT NULL` e o MySQL proíbe `SET NULL` em FK composta que inclua uma coluna `NOT NULL`.
- **Decisão:** adicionada uma coluna auxiliar nullable `financial_entries.responsible_member_household_id`, que só é preenchida (pela camada de persistência, nunca manualmente) quando `responsible_member_id` está definido, e sempre com o mesmo valor de `household_id`. Uma FK composta `financial_entries_responsible_member_household_fk (responsible_member_id, responsible_member_household_id) → household_members(id, household_id)` garante no banco que o par pertence a um household_member real do household correto. Uma `CHECK` (`financial_entries_responsible_member_household_check`) garante que a coluna auxiliar é nula exatamente quando `responsible_member_id` é nulo, e igual a `household_id` quando não é. Um `unique(id, household_id)` foi adicionado em `household_members` como alvo da FK, seguindo o mesmo padrão já usado por `categories`/`monthly_periods`. Aplicada como migration incremental versionada (`database/migrations/0001_responsible_member_household_integrity.sql`), **sem alterar a migration inicial** (`0000_initial_financial_domain.sql`, intocada). Aplicada **somente** em `finanhouse_dev`; `finanhouse_prod` continua inexistente; nenhum dado real ou sintético foi inserido — a correção é puramente estrutural. Preencher a coluna auxiliar é responsabilidade exclusiva da camada de persistência (futuros repositórios Drizzle) — nunca deve ser escrita manualmente fora dela.
- **Desvio do plano original — `ON DELETE RESTRICT`, não `SET NULL`:** o plano original (e o requisito inicial deste bloco) previa preservar `ON DELETE SET NULL` na FK composta, idêntico ao comportamento da FK simples anterior. Na primeira tentativa real de aplicação, o MySQL 8 rejeitou a FK composta com o erro `3823` (`ER_CHECK_CONSTRAINT_CLAUSE_USING_FK_REFER_ACTION_COLUMN`): uma coluna não pode participar de uma `CHECK` constraint se também for alvo de uma ação referencial que a modifica automaticamente (`SET NULL`/`CASCADE`) em uma foreign key — e ambas as colunas da FK composta (`responsible_member_id`, `responsible_member_household_id`) são referenciadas pela `CHECK`. `SET NULL` e a `CHECK` são, portanto, mutuamente incompatíveis no MySQL. A FK composta foi trocada para `ON DELETE RESTRICT`, mantendo a `CHECK` — a garantia de integridade permanece 100% no banco (FK + CHECK); a única mudança de comportamento é que excluir fisicamente um `household_member` ainda referenciado por alguma movimentação passa a ser **bloqueado** em vez de silenciosamente limpar a referência. Como `household_members` já usa exclusão lógica (`status`/`removed_at`) — nunca `DELETE` físico —, o impacto prático é nulo.
- **Incidente durante a aplicação:** a primeira tentativa de aplicar a migration (ainda com `SET NULL`) falhou no 5º de 6 statements (criação da FK composta). Como DDL não é transacional no MySQL/InnoDB (cada `ALTER TABLE`/`CREATE INDEX` gera um commit implícito próprio, independente da "transação" JS do migrator do Drizzle), os 4 statements anteriores (remoção da FK simples antiga, adição da coluna auxiliar, adição do `unique(id, household_id)`, adição da `CHECK`) já haviam sido aplicados permanentemente antes da falha, deixando `finanhouse_dev` em um estado parcial — o journal do Drizzle não refletia isso (só registra a migration inteira, ao final). O erro foi diagnosticado com um script de diagnóstico temporário e somente leitura (nunca versionado), que reexecutou isoladamente o statement 5 já revisado para capturar a mensagem real do MySQL — exceção pontual e autorizada explicitamente pelo proprietário à regra geral de nunca exibir erro bruto de banco, justificada porque um erro de DDL/constraint não contém host, usuário ou senha. Após identificar a causa raiz e corrigir o schema (`RESTRICT`), o estado parcial foi revertido com 4 statements de recuperação (também temporários, também nunca versionados, também autorizados explicitamente em separado), confirmado por auditoria somente leitura, e só então a migration corrigida foi aplicada — com sucesso, em uma segunda autorização explícita separada.
- **Motivos:** a FK simples nunca garantiu a regra "responsável pertence ao mesmo household" no banco; qualquer bug de repositório futuro poderia associar um membro de outro household sem violar nada no MySQL. RESTRICT com CHECK fecha essa lacuna definitivamente, sem trigger (explicitamente vetado) e sem alterar a migration inicial já aplicada.
- **Alternativas consideradas:** manter `SET NULL` e remover a `CHECK` — rejeitada por reabrir a lacuna que esta correção existe para fechar (a FK sozinha não impede que a coluna auxiliar seja preenchida com um household diferente do da própria movimentação); usar trigger para sincronizar a coluna auxiliar — rejeitada, vetada explicitamente pelo escopo deste bloco; coluna gerada (`GENERATED ALWAYS AS`) — não avaliada a fundo por também ter restrições próprias de interação com FKs de ação automática no MySQL, e por RESTRICT+CHECK já resolver o problema sem essa complexidade adicional.
- **Consequências:** `category_budgets` e qualquer tabela nova exigem migrations incrementais futuras, geradas e revisadas da mesma forma — nunca edição manual das migrations já aplicadas; a P2 de integridade do membro responsável (Blocos 03/04) está encerrada; RF-05 não é declarado concluído (repositórios reais, endpoints de API e integração do frontend continuam pendentes); qualquer futuro `DELETE` físico de `household_member` referenciado por uma movimentação será bloqueado pelo banco — comportamento novo, documentado aqui para não ser redescoberto por acidente.
- **Status:** Vigente

Resultado sanitizado confirmado: provider `aiven`, ambiente `development`, banco `finanhouse_dev`, conectividade bem-sucedida, MySQL `8.4.8`, banco ativo correspondente ao configurado, TLS ativo, `rejectUnauthorized: true` e verificação padrão de hostname preservados. Nenhuma migration foi aplicada, nenhum seed foi executado, nenhuma tabela foi criada nesta verificação. A pendência P2 de TLS citada acima está **encerrada** a partir desta data (ver `Docs/03_contracts/contrato_banco_dados.md`, seção 12); a pendência P2 de aplicação da migration inicial **continua aberta**.
- **Status:** Vigente

### DT-06 — Histórico mensal somente leitura em memória

- **Data:** 2026-07-26
- **Contexto:** O Bloco 10 precisava decidir como expor o histórico de competências e movimentações anteriores sem introduzir um segundo estado financeiro nem abrir uma via alternativa de mutação fora das áreas de gestão já existentes (Movimentações, Planejamento).
- **Decisão:** Implementar o Histórico como derivação pura em `apps/web/src/view-models/history-view-model.ts`, consumindo a mesma fonte compartilhada do `FinanceDemoProvider` via `useFinanceDemo()`. A rota `/historico` é estritamente consultiva: nenhum componente de `components/history/` despacha ações no reducer, e não há nenhum caminho de criação, edição, exclusão, fechamento ou reabertura de competência a partir dela. Os resumos financeiros reaproveitam `calculateMonthlySummary` (`@finanhouse/domain`), sem reimplementar nenhuma fórmula. Os filtros (ano, status da competência, status da movimentação) e a competência selecionada vivem apenas como estado local de apresentação da página (`useState`), nunca escritos em `FinanceDemoState`. Nenhuma persistência é implementada nesta etapa.
- **Motivos:** impedir duplicação de estado financeiro (uma segunda fonte de movimentações/competências divergiria do Dashboard/Movimentações/Comparativo/Planejamento); evitar mutações acidentais em uma área pensada exclusivamente para consulta; manter consistência de arquitetura com as quatro áreas funcionais já entregues; preparar a substituição futura do estado demonstrativo por uma API real sem exigir mudança de interface (`useFinanceDemo()` mantém o mesmo contrato).
- **Alternativas consideradas:** permitir ações rápidas de correção (ex.: reativar uma movimentação cancelada) diretamente do Histórico — rejeitada por misturar uma área de consulta com uma área de gestão, contrariando o objetivo do bloco ("estritamente consultivo") e abrindo uma segunda via de mutação para as mesmas regras já cobertas por Movimentações.
- **Consequências:** alterações feitas em qualquer área de gestão (Movimentações, Planejamento) são válidas somente durante a sessão do navegador e refletem no Histórico em tempo real, por lerem o mesmo `state`; recarregar a página restaura as fixtures, inclusive no Histórico; dados históricos definitivos (competências fechadas de verdade, auditáveis) dependem da persistência real (API + MySQL), ainda bloqueada pelo TLS (Bloco 04); o refinamento visual do Histórico permanece como P3 no backlog de design, junto das demais áreas.
- **Status:** Vigente

### DT-05 — Planejamento mensal: limite de orçamento permite alteração em competência "review", diferente de movimentações comuns

- **Data:** 2026-07-26
- **Contexto:** O Bloco 09 precisava decidir se definir/editar/remover um limite de orçamento por categoria deveria seguir a mesma regra de `assertPeriodAllowsEntryChanges` usada por movimentações comuns — que bloqueia a competência `review` por padrão, exigindo `allowReviewAdjustment: true` explícito (hoje reservado a estorno/correção/reativação).
- **Decisão:** `packages/domain/src/planning/category-budget-rules.ts` expõe `assertPeriodAllowsBudgetChanges`, que chama `assertPeriodAllowsEntryChanges(period, { allowReviewAdjustment: true })` sempre — ou seja, limites de orçamento podem ser criados/editados/removidos em competências `open` **ou** `review`; apenas `closed` bloqueia.
- **Motivos:** planejar/ajustar limites é uma atividade de acompanhamento (não altera o histórico financeiro realizado), naturalmente mais frequente durante a revisão de fechamento do mês (quando o usuário está justamente comparando limite vs. realizado); tratar isso como "ajuste de revisão" evita impedir a única situação em que o planejamento é mais útil.
- **Alternativas consideradas:** replicar a regra padrão de movimentações comuns (bloquear `review` por padrão) — rejeitada por criar fricção desnecessária exatamente no momento em que o planejamento é mais consultado/ajustado.
- **Consequências:** criação de um **novo** limite continua restrita à competência atual do estado (mesma convenção de criação de movimentações — `Docs/02_architecture/estado_temporario_frontend.md`, seção 5), mas editar/remover um limite existente funciona em qualquer competência não fechada, inclusive ao navegar para uma competência diferente da atual no seletor da página.
- **Status:** Vigente

### DT-03 — Roteamento do frontend: migração para `react-router@8.3.0` (pin exato)

- **Data:** 2026-07-25
- **Contexto:** DT-02 havia fixado `react-router-dom@7.18.1`, aceitando como risco documentado (não eliminado) a vulnerabilidade alta GHSA-qwww-vcr4-c8h2 ("RSC Mode CSRF Bypass"), com o argumento de que ela só afeta aplicações usando APIs instáveis de RSC, não usadas pelo Finanhouse. Antes de integrar o Bloco 07 à `main`, foi identificado que existe correção oficial publicada: a faixa afetada pela advisory é `>=7.12.0, <8.3.0` — ou seja, `8.3.0` é exatamente a primeira versão corrigida (confirmado na própria descrição oficial da GHSA). Em React Router v8, o pacote `react-router-dom` foi descontinuado: aplicações em modo declarativo (client-side, sem framework mode) passam a importar diretamente do pacote único `react-router`.
- **Decisão:** Migrar de `react-router-dom@7.18.1` para `react-router@8.3.0`, pin exato (sem `^`/`~`), antes de qualquer merge do Bloco 07 na `main`. Todos os imports usados pelo projeto (`BrowserRouter`, `MemoryRouter`, `Routes`, `Route`, `Navigate`, `NavLink`, `Outlet`, `useLocation`) passaram a vir de `'react-router'`. Nenhum pacote de modo framework/SSR/RSC foi instalado (`@react-router/dev`, `@react-router/node`, `create-react-router`) — o projeto continua uma SPA declarativa client-side sobre Vite, sem loaders/actions de servidor, sem RSC, sem SSR/prerendering.
- **Motivos:** (1) `8.3.0` contém a correção oficial da vulnerabilidade, em vez de apenas documentá-la como não aplicável; (2) elimina as duas vulnerabilidades altas de produção acusadas pelo `npm audit`, não apenas as justifica; (3) a migração v7→v8 é compatível com o uso puramente declarativo já feito pelo projeto; (4) peer/engine requirements de `8.3.0` (`react`/`react-dom` `>=19.2.7`, Node `>=22.22.0`) já são atendidos pelo projeto (`react`/`react-dom` em `^19.2.7`, Node local `v24.16.0`); (5) `react-router-dom` deixou de existir como pacote principal a partir da v8 (não há release `8.x` publicado dele); (6) não há justificativa para manter uma dependência com vulnerabilidade alta aceita como risco quando existe correção oficial compatível disponível.
- **Alternativas consideradas:** manter `react-router-dom@7.18.1` com o risco documentado em DT-02 (rejeitada pelo proprietário: "não faz sentido aceitar duas vulnerabilidades altas em produção quando existe correção oficial compatível"); aguardar uma futura versão `7.x` corrigida (rejeitada — a correção só existe a partir de `8.3.0`, não há backport para a linha `7.x`).
- **Consequências:** `react-router-dom` removido das dependências de `apps/web`; qualquer novo código de roteamento deve importar de `'react-router'`; nenhuma API de modo framework (loaders/actions/`RouterProvider`/`createBrowserRouter`/RSC/SSR) deve ser usada, mantendo o projeto como SPA declarativa; **supera DT-02**, que permanece registrada abaixo apenas como histórico da decisão anterior.
- **Status:** Vigente

### DT-02 — Roteamento do frontend: `react-router-dom@7.18.1` (pin exato)

- **Data:** 2026-07-25
- **Contexto:** Bloco 07 precisa de navegação real entre "Visão geral" e "Movimentações". `react-router-dom` foi autorizado explicitamente pelo proprietário como a única dependência de roteamento a instalar. Ao instalar, `npm audit` acusou vulnerabilidades em praticamente toda a linha 7.x publicada: a versão mais recente (`7.18.1`) está na faixa afetada por GHSA-qwww-vcr4-c8h2 (CSRF bypass em "RSC Mode"); versões `6.0.0`–`7.17.0` (incluindo `7.11.0`, cogitada como downgrade "seguro") estão na faixa afetada por 13 outras advisories (XSS, open redirect, RCE via deserialização, DoS) — a maioria específica de SSR/RSC/prerendering/single-fetch/server actions.
- **Decisão:** Fixar exatamente `react-router-dom@7.18.1` (sem `^`), a versão mais recente disponível. Verificado via a própria descrição da GHSA-qwww-vcr4-c8h2 que essa vulnerabilidade **só afeta aplicações usando as APIs instáveis de RSC** ("This only affects your application if you are using the unstable RSC APIs") — o Finanhouse usa apenas o modo declarativo client-side (`BrowserRouter`/`Routes`/`Route`/`Link`/`NavLink`/`useNavigate`), sem RSC, sem loaders/actions de servidor, sem SSR/prerendering. Todas as demais 13 advisories (faixa `6.0.0`–`7.17.0`) não se aplicam a `7.18.1`, que é posterior a esse intervalo.
- **Alternativas consideradas:** `7.11.0` (evita a CSRF/RSC, mas cai nas 13 advisories da faixa anterior, incluindo open-redirect em `<Link>`/`useNavigate` — mais relevante para uso client puro que a CSRF de RSC); outro roteador (explicitamente proibido pelo prompt do Bloco 07).
- **Consequências:** Pin exato (não `^7.18.1`) para que uma atualização automática não reintroduza silenciosamente uma versão pior; reavaliar quando uma versão publicada corrigir GHSA-qwww-vcr4-c8h2 sem reabrir as demais.
- **Status:** Superada pela DT-03 antes da integração do Bloco 07

### DT-01 — Persistência: Drizzle ORM + mysql2

- **Data:** 2026-07-25
- **Contexto:** O MySQL do Finanhouse existe na Clever Cloud mas está confirmado vazio (Bloco 02). Era preciso decidir a camada de acesso a dados antes de modelar o schema.
- **Decisão:** Drizzle ORM (schema tipado + geração de migrations) sobre `mysql2` (driver real). Ver ADR completo em `Docs/02_architecture/adr_001_persistencia_drizzle_mysql2.md`.
- **Alternativas consideradas:** `mysql2` puro (mais simples, mas migrations e tipagem manuais); Prisma/TypeORM/Sequelize/Knex (mais peso/complexidade do que o projeto precisa).
- **Consequências:** Schema TypeScript vira fonte de verdade; migrations são geradas e revisadas, nunca aplicadas via `drizzle-kit push`; aplicação de migration exige autorização explícita.
- **Status:** Vigente
